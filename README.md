End-to-end retail demand forecasting system, from synthetic data to a forecasting API. Compares six models on a leakage-free test and serves the best one.

---

## Business Problem

Inaccurate demand forecasts lead to overstocking or stockouts. This pipeline gives retail teams a data-driven forecast deployable as an API.

---

## Model Results

Store 1, trained on 1 Jan 2020 – 9 Mar 2023 and tested on the remaining 285 days (10 Mar – 31 Dec 2023). Every model forecasts the whole test period without seeing any test-period sales. Data is synthetic, generated by `01_generate_data.py` (output committed in `data/raw/`).

| Model | MAE | RMSE | MAPE |
|---|---|---|---|
| **Random Forest** | **57.5** | **81.6** | **5.3%** |
| Linear Trend | 161.7 | 195.0 | 15.1% |
| Moving Average (3-day) | 237.2 | 289.7 | 25.1% |
| Naive | 262.3 | 319.1 | 28.4% |
| Exponential Smoothing | 306.5 | 364.2 | 33.4% |
| Seasonal Naive | 370.3 | 452.7 | 39.4% |

Stores 2 and 3 give 5.8% and 5.1% MAPE with the same setup.

**How the Random Forest avoids leakage.** It uses only features that are known before the forecast day (`src/forecast_features.py`): calendar fields, the holiday calendar, planned promotions, and sales on the same weekday one year earlier. Test-period features read history from the training period only. The same feature builder is used for training and by the API.

**Why the error is low.** The synthetic sales follow a smooth yearly cycle, a weekend bump, holiday and promotion multipliers, plus noise of about ±50 units. A model that learns those rules can get close to the noise floor. Expect higher error on real sales data.

**Fixed on 16 Oct 2026.** An earlier version reported 4.7% MAPE. That score came from rolling-average features that included the same day's sales and from one-day-ahead lags in a 285-day test. Both are now fixed, and the rolling features in `src/preprocessor.py` are shifted by one day.

Exponential Smoothing does worse than the naive baseline here, which is worth investigating before using it on real data.

## Quickstart

```bash
git clone https://github.com/deepanshu0110/retail-sales-forecasting.git
cd retail-sales-forecasting
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python 01_generate_data.py
python 02_preprocess_data.py
python 03_run_eda.py
python 04_train_models.py
python 05_deployment_api.py
```

## API Usage

```bash
curl -X POST http://localhost:5000/forecast -H 'Content-Type: application/json' -d '{"store_id": 1, "days_ahead": 7, "model": "best", "promotions": [0, 0, 1, 0, 0, 0, 0]}'
```

The API is a Flask app on port 5000. It forecasts the days right after the last date in the data, building each day's features separately. Optional fields: `model` (`best`, `random_forest`, `linear_trend`, or `fallback`) and `promotions` (a list of 0/1 planned promotions, one per day). Other endpoints: `GET /health`, `GET /models`, `POST /batch_forecast`. The `fallback` model is a seasonal average with random noise, used only if no trained model is available.

## Tests

```bash
pip install pytest
pytest tests/ -v
```

The tests checks that features never read the target day's sales, runs the pipeline, and checks the API forecast varies by day and responds to promotions. GitHub Actions runs them on every push.
